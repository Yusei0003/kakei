# kakei 設計書

LINEで送るだけの家計管理システム。2026-08-08 時点。

> 仕様を変更するときは、この文書と `supabase/schema.sql`、`src/lib/categories.ts` の
> 3箇所を同時に更新すること。

---

## 1. 目的と前提

家計管理のために、支出と収入をできるだけ手間なく記録し、「何にいくら使ったか」を後から
見返せるようにする。記録の入口はすべてLINEに集約し、専用アプリを開く習慣を必要としない。

**前提**

- 利用者は1人。家族共有や権限分離は考えない。
- ランニングコストは月額0円を目標にする。各サービスの無料枠内に収める。
- レシート画像は金額を読み取ったあと破棄し、保存しない。
- 口座は2つ（ゆうちょ銀行・岩手銀行）、決済手段はPayPayと楽天カード、加えて現金。

## 2. システム構成

| 層 | 採用 | 役割 | コスト |
|---|---|---|---|
| 入口 | LINE Messaging API | 写真・ファイル・テキストの受信、確認質問の送信 | 無料 |
| サーバー | Vercel Serverless Functions | Webhook受信、解析、分類、保存 | 無料枠 |
| OCR | Google Cloud Vision API | レシート画像から文字を抽出 | 無料枠 月1,000件 |
| データベース | Supabase (PostgreSQL) | 取引・学習データ・会話状態の保存 | 無料枠 |
| 画面 | Next.js + Recharts | カテゴリ別・月別の集計表示 | 無料枠 |

カテゴリ判定にLLMを使う案もあったが、店名を一度覚えれば十分な精度が出るため採用しなかった。
結果として従量課金される要素がなくなり、月額は完全に0円になる。

## 3. 処理フロー

入力の種類は5つあるが、解析を終えた時点で「日付・金額・相手先・収支の別」という共通の形に
揃える。以降の判定・保存・確認の流れは、どの入力から来たかを問わず同一になる。

```
レシート写真 ┐
テキスト入力 │
PayPay CSV  ├→ LINE Webhook →  OCR/パース  →  収支の判定    →  Supabase ┬→ LINEで確認
クレカ明細   │   (署名検証)      除外ルール     学習済カテゴリ              └→ ダッシュボード
通帳CSV     ┘                                 重複検出
```

**判定の順序**

1. **除外ルール** — ATM引出やPayPayチャージなど、家計の増減を伴わない内部移動をここで落とす。
2. **収支の判定** — 入金か出金か、通帳の摘要やテキストの書き方から収入・支出を決める。
3. **学習済カテゴリの適用** — 過去に答えた店名なら自動でカテゴリが決まる。
4. **重複検出** — 別の経路から同じ買い物が二重に入っていないか照合する。
5. ここまでで全部決まれば**確定**。決まらなければ**確認キュー**へ。

## 4. データモデル

支出・収入をまとめて扱う `transactions` テーブル。`kind` で収支を分け、`account` で
どの口座・決済手段かを持たせる。

### transactions — 取引

| 列 | 型 | 説明 |
|---|---|---|
| `id` | uuid | 主キー |
| `occurred_at` | timestamptz | 取引日時。CSVはJSTとして解釈する |
| `amount` | integer | 金額。収支の別は符号ではなく `kind` で表す |
| `kind` | text | `expense` / `income` |
| `category` | text | 支出13種・収入4種のいずれか。未確定はnull |
| `account` | text | `yucho` / `iwate` / `paypay` / `rakuten_card` / `cash` |
| `store_name` | text | 店名・振込先・摘要 |
| `memo` | text | 自由記述 |
| `source` | text | `receipt` / `manual` / `paypay` / `credit_card` / `bank` |
| `source_ref` | text | 取引番号や明細ID。同一ファイルの再取込を弾く一意キー |
| `is_transfer` | boolean | 個人間送金・振込。カテゴリ学習の対象外にする印 |
| `status` | text | `pending_category` / `pending_duplicate` / `confirmed` |
| `duplicate_of` | uuid | 重複と確定した場合、残す方のレコードを指す |
| `line_user_id` | text | LINEのユーザーID |

### store_category_map — カテゴリ学習

正規化した店名とカテゴリの対応を持つ。`(line_user_id, store_pattern)` で一意。
一度答えた店を二度聞かないための土台。

### line_conversation_state — 会話状態

確認待ちの取引IDを並べたキュー、いま質問中の取引、何を聞いているか（カテゴリか重複か）を
保持する。CSVを取り込むと確認対象がまとめて発生するため、LINE上で1件ずつ順に処理するのに使う。

## 5. カテゴリ定義

実際の取引履歴に出てきた費目から決めた。LINEのクイックリプライは最大13個までのため、
支出はちょうど上限の13個に収めている。

### 支出（13種）

|---|---|---|
| `food` | 食費 | コンビニ各社、マイヤ、中華食堂熊谷、熊谷珈琲店、Coke ON |
| `daily_goods` | 日用品 | キャンドゥ |
| `transport_car` | 交通費・車 | カメイ燃料代、ETCカード売上 |
| `communication` | 通信費 | 楽天モバイル、So-net、au電話料金 |
| `insurance` | 保険 | 住友生命保険、市町村職員共済組合 |
| `subscription` | サブスク・娯楽 | Amazonプライム会費、DMM.com、Apple.com、スポーツデポ |
| `health` | 医療・健康 | マイプロテイン、メディカルブレス、プレミアムウォーター |
| `shopping` | 通販・買い物 | Amazon、楽天市場、HOLO BELL |
| `drinking` | 飲み会代 | 飲み会の支払い・割り勘 |
| `housing` | 家賃・住居費 | JC ダイトウヤチン（月額57,739円） |
| `utilities` | 水道光熱費 | 水道料金 |

### 収入（4種）

| ID | 表示名 | 実データでの該当例 |
|---|---|---|
| `salary` | 給与 | 陸前高田市会計管理者からの振込 |
| `honorarium` | 謝金 | 現金で受け取る謝金。LINEにテキストで登録する |
| `interest` | 利息 | 決算利息 |
| `other_income` | その他 | 上記以外の入金 |

## 6. 入力ソース仕様

| 入力 | 形式 | 金額の取得 | カテゴリの決定 | 収支 |
|---|---|---|---|---|
| レシート写真 | 画像 | Vision APIでOCRし「合計」付近の数字を採用 | LINEのボタンで選択 | 支出 |
| テキスト入力 | 自由文 | 文中の最初の数値。例 `ランチ 800円` | 残りの語を店名として学習を照会 | 両方 |
| PayPay | CSV / UTF-8 | 出金金額の列 | 取引先の店名から学習を照会 | 支出 |
| 楽天カード | PDF | 利用金額の列 | 利用店名から学習を照会 | 支出 |
| 通帳 | CSV / Shift_JIS | 受入金額・払出金額の列 | 摘要のパターンから判定 | 両方 |

### テキスト入力での収入の書き方

テキストは既定では支出として解釈する。文中に「**謝金**」という語が含まれていた場合のみ、
収入（謝金）として記録する。現金でもらう謝金を想定した規則。

- `ランチ 800円` → 支出・食費（学習済みなら自動）
- `謝金 5000円` → 収入・謝金

### PayPay CSVの取り込み対象

| 取引内容 | 扱い | 理由 |
|---|---|---|
| 支払い | 支出として記録 | 店舗での決済 |
| 送った金額 | 毎回カテゴリを確認 | 同じ相手でも用途が毎回変わるため学習させない |
| チャージ | 除外 | 銀行からPayPayへの資金移動にすぎない |
| ポイント、残高の獲得 | 除外 | 支出ではない |

## 7. 通帳の分類ルール

通帳は他の入力と性質が違う。行の大半が家計の増減を伴わない**内部移動**であり、そのまま
取り込むと支出が実態の数倍に膨れ上がる。実際、提供された岩手銀行の履歴953行のうち385行が
PayPayチャージ、156行がATM引出だった。除外ルールが設計の中心になる。

### 対応する2つの形式

口座ごとに列構成が異なるため、ヘッダー行を見て自動判別する。

| 口座 | ヘッダー | 日付形式 | 摘要の位置 |
|---|---|---|---|
| ゆうちょ銀行 | `取引日, 入出金明細ID, 受入金額, 払出金額, 詳細1, 詳細2, 現在高` | `20260707` | 詳細1・詳細2 |
| 岩手銀行 | `年月日, お支払金額, お預かり金額, 取引内容, 差引残高, メモ` | `2026-07-07` | 取引内容 |

どちらも文字コードは **Shift_JIS** で、摘要は**半角カナ**。UTF-8として読むと全行が
文字化けするため、デコード処理を挟む必要がある。

### 摘要パターンごとの扱い

| 摘要パターン | 意味 | 扱い | 件数 |
|---|---|---|---:|
| `RS ﾍﾟｲﾍﾟｲ` / `RS PAYPAY` | PayPayへのチャージ | 除外 | 406 |
| `ATMｼﾊﾗｲ` | ATMからの現金引出 | 除外 | 156 |
| `ﾓｸﾃｷﾖｷﾝﾌﾘｶｴ` | 目的預金への振替 | 除外 | 120 |
| `ｾﾌﾞﾝATM*` / `ｺﾝﾋﾞﾆATM*` / `ﾀｺｳATM` | ATMからの現金引出 | 除外 | 50 |
| `ATMﾆﾕｳｷﾝ` | ATMへの現金預入 | 除外 | 3 |
| `ｽﾏｰﾄﾂｳﾁﾖｳｷﾘｶｴ` | 通帳の切替手続き（金額0） | 除外 | 1 |
| `カード` / `ﾗｸﾃﾝｶ-ﾄﾞ(ｶ` | クレジットカードの引落 | 除外（下記の注意を参照） | 4 |
| `ﾘｸｾﾞﾝﾀｶﾀｼｶｲｹｲ…` / 詳細1が「給与」 | 給与の振込 | 収入・給与 | 72 |
| `ｹﾂｻﾝﾘｿｸ` | 決算利息 | 収入・利息 | 4 |

| 詳細1が「育英」/ 日本学生支援機構 | 奨学金の返済 | 支出・ローン | 1 |
| `ﾘﾖｳﾃｽｳﾘﾖｳ` / `ﾌﾘｺﾐﾃｽｳﾘﾖｳ` | ATM・振込手数料 | 支出・その他 | 85 |
| `…ｷﾖｳｻｲｸﾐｱｲ` / `…ｹﾝｺｳﾌｸﾘｷｺｳ` | 共済組合・福利厚生 | 確認 | 7 |
| `ﾌﾘｺﾐ` | 振込（用途が毎回異なる） | 毎回確認 | 5 |
| 個人名 | 個人からの入出金 | 毎回確認 | 4 |

### 注意: クレカ引落を除外することの副作用

通帳の「カード」行を除外するのは、その中身がクレカ明細側で1件ずつ記録される前提に立っている。
クレカ明細PDFの自動解析は12章のとおり解決済みだが、**その月の明細をまだLINEに送っていない
間は、カード決済分がまるごと家計簿から抜けた状態になる**点は変わらない。

現状は運用でカバーする想定（通帳を送ったら忘れずにその月のクレカ明細も送る）。もし取りこぼしが
頻発するようなら、通帳のカード引落行を検出した時点で「明細はまだですか？」とLINEが確認する
仕組みを追加する余地がある。

### 残高による検算

どちらの形式にも残高列がある。前の行の残高に入出金を加減した値が次の行の残高と一致するかを
検算すれば、パースの取りこぼしをその場で検出できる。取り込み結果の信頼性を確認する手段として
実装する。

## 8. カテゴリ学習

「一度答えたら次から聞かない」を実現する仕組み。LINEでカテゴリを選んだとき、その店名と
カテゴリの対応を保存し、以後は同じ店の取引を自動で分類する。

### 店名の正規化

PayPayやクレカの店名は「チェーン名 - 支店名」の形をとる。支店ごとに聞き直すのは無駄なので、
チェーン名の部分を学習キーにする。

- `セブン-イレブン - 陸前高田竹駒町` → `セブン-イレブン`
- `セブン-イレブン - 大船渡宮の前` → 同じキーに当たるので聞かれない

### 収支の別まで含めて学習する

学習のキーは `(利用者, 正規化した店名・摘要, 収支の別)`。同じ摘要でも入金と出金では
意味が変わるため、収支の別を含めないと「給与の振込元と同じ相手への出金」に給与カテゴリが
適用されてしまう。収入・支出それぞれで独立に学習する。

### 銀行明細の周期学習

銀行明細の固定費・定期収入については、発生日と金額の観測範囲も蓄積し、次回以降
「いつもと違う」取引だけ確認する。閾値は固定値ではなく**観測済みの範囲そのもの**を
基準にする自己較正型とする。

| 明細 | 実データでの挙動 | 結果 |
|---|---|---|
| `JC ﾀﾞｲﾄｳﾔﾁﾝ`（家賃） | 毎月27日・57,739円で範囲が狭いまま | 日付のズレ・金額の変化を検知できる |
| `水道料金` | 毎月27日だが金額が季節変動 | 範囲が広がり季節変動は許容 |
| `ﾘｸｾﾞﾝﾀｶﾀｼｶｲｹｲｶﾝﾘｼﾔ`（給与） | 日付も金額も大きくばらつく | 範囲が広がりほぼ発火しない |

日付の観測幅が20日を超えた明細は、日付が手がかりにならないと判断して日付チェックを
止める。周期チェックは銀行明細に限定する（コンビニ決済のように日付も金額もばらつく
ものに適用すると毎回確認が出てしまうため）。

### 学習しないもの

相手が同じでも用途が毎回変わるため、次のものは学習の対象外とし、毎回カテゴリを尋ねる。

- PayPayの「送った金額」（個人間送金）
- 通帳の「振込」（摘要が `ﾌﾘｺﾐ` のもの）

なお個人名あての入出金は、当初は学習対象外とする案だったが、聞かれる回数を減らす方を
優先して**学習対象に含めている**。

学習した対応はダッシュボードから一覧・修正できるようにする。誤って覚えた店を後から直せないと、
間違いが延々と自動適用されてしまうため。

## 9. 重複検出

同じ支出が別の経路から二重に入るのを防ぐ。性質の違う2種類がある。

**同一ソースの重複** — 同じCSVを二度送った場合など。`(source, source_ref)` に一意制約を張り、
データベース側で弾く。PayPayの取引番号、通帳の明細ID、クレカ明細の行から生成したキーを使う。
利用者への確認は不要なので黙ってスキップし、件数だけ報告する。

**ソースをまたぐ重複** — レシート写真で記録した買い物が、月末にPayPayのCSVからも入ってくる
場合など。金額が一致し、日付が**前後2日以内**で、かつ別のソースから来た取引を重複候補とみなす。
機械的には判断できないため、LINEで「重複としてまとめる」「別々の支出として記録」を選んでもらう。
まとめる場合はレコードを削除せず、`duplicate_of` に残す方のIDを入れる。集計からは外れるが、
どの取引がどれと統合されたかの履歴は残る。

**ルールで先に潰す重複** — PayPayチャージ（通帳側とPayPay側の両方に現れる）とクレカ引落
（通帳側と明細側）は、構造的に必ず重複する。これは確認を挟まず、通帳側を除外することで
機械的に解決する。

## 10. LINE確認フロー

CSVを1本送ると数十件から数百件の取引が一度に発生する。全件をLINEで確認させると通知が
溢れるため、**自動で決まったものはまとめて報告し、決まらなかったものだけ1件ずつ聞く**方式をとる。

取り込み直後の返信:

```
PayPay明細を取り込みました。
自動記録: 32件
確認が必要: 4件
重複でスキップ: 0件
対象外（チャージ等）: 24件
```

続けて、確認が必要な1件目についてカテゴリ選択のボタンが表示される。回答すると次の1件が
出てくる。キューが空になるまでこれを繰り返す。

**確認の種類**

- **カテゴリ選択** — 取引の内容とともに、カテゴリのボタンを提示する。
- **重複確認** — 既存の取引と並べて見せ、まとめるか分けるかを選んでもらう。分けた場合、
  カテゴリが未確定ならそのまま続けてカテゴリを聞く。

古いメッセージのボタンを後から押しても、すでに別の質問に進んでいれば無視する。キューの順序と
実際の回答がずれないようにするため。

## 12. 制約とリスク

### 楽天カードの明細PDFについて（解決済み）

当初 `pdf-parse`（pdf.js系）で解析したところ、フォントの都合で文字がほとんど取得できな
かった。MuPDFの公式Node.jsバインディング（`mupdf`）に切り替えたところ問題なく抽出でき、
実際の明細PDF（2026年07月分、20取引・合計61,325円）で1円のズレもなく一致することを
確認済み。CSVダウンロードへの切り替えや画像化してのOCRは不要になった。

テキスト抽出後は1項目1行（日付→店名→支払者→支払方法→金額...の順）で並ぶ形式のため、
単一行の正規表現ではなく、行のまとまり（ブロック）としてパースする方式に変更した。
楽天カード以外のカード会社ではレイアウトが異なる可能性があるため、抽出できた文字数が
極端に少ない場合と、行の並びが想定と合わず取引が1件も取れなかった場合の両方を検知し、
その場合はLINEに「CSV形式があればそちらを」と案内するフォールバックは残している。

### その他の制約

- **「謝金」の誤判定** — 謝金を支払った場合も収入として記録されてしまう。ダッシュボードは
  未確定の取引と学習済みカテゴリしか編集できないため、確定済みの誤りは現状Supabaseを
  直接操作して直す必要がある（確定済み取引の編集画面は未実装）。
- **ダッシュボードの集計方式** — 個人利用の想定データ量を前提に、確定済み取引を全件
  取得してJS側でJST月ごとに集計している。件数が大きく増えた場合はSQL側の集計に
  切り替える必要がある。
- **OCRの精度** — 「合計」付近の数字を採る単純な規則のため、割引やお預かり金額を拾う
  可能性がある。読み取った金額はLINEに表示し、明らかな誤りに気づけるようにする。
- **取引日時の粒度** — レシート写真とテキスト入力は送信時刻を取引日時として記録する。
  後日まとめて入力すると日付がずれる。
- **Vision APIの無料枠** — 月1,000件を超えると課金される。個人利用では到達しない見込みだが、
  超過時は月額0円の前提が崩れる。
- **service roleキーの扱い** — Supabaseのservice roleキーは行レベルセキュリティを無視する。
  サーバー側の環境変数としてのみ設定し、クライアントに露出させない。
